# behavior-spec-extraction

기존 구현을 읽어, 그 기술을 모르는 사람도 검수할 수 있는 **관측 가능한 동작** 명세로 reverse-engineer한다.

## 왜 만들었나

마이그레이션(Unity→React, UIKit→SwiftUI)이나 인수인계 전에 "지금 이게 뭘 하는지"를 적어둔 문서가 없다. 코드를 읽을 줄 아는 사람만 동작을 알고, 기획자나 다른 스택 개발자는 맞는지 틀린지 판단할 수 없다. 구현은 있는데 요구사항 문서가 없으면 무엇이 의도이고 무엇이 사고인지도 구분이 안 된다.

## 무엇을 해주나

- 기능 경계를 "사용자 눈에 하나로 보이는 동작" 단위로 자르고 먼저 동의를 받는다.
- 코드에서 발동 계기 · 받는 값 · 밖에 남는 변화 · 실패 경로만 뽑는다. 내부 자료구조와 호출 순서는 버린다.
- Goal · Triggers · Inputs · Outputs · Edge cases · Acceptance 6섹션 Markdown으로 쓴다. 클래스 · 메서드 · 프레임워크 용어 없이.
- `scripts/lint_spec.py`가 구현 누출과 사람이 손으로 따라 할 수 없는 Acceptance를 막는다.

산출물은 코드 블록이 없는 명세 `.md`다. 예시는 [references/example-spec.md](references/example-spec.md).

## 어떻게 쓰나

bundle에 없다. 폴더 복사로 설치한다 → [설치](../docs/install.md)

> 이 코드 명세로 뽑아줘
> 마이그레이션 전에 현재 동작을 문서로 남겨줘

절차는 [SKILL.md](SKILL.md), 번역 규칙은 [references/translation-rules.md](references/translation-rules.md)에 있다.

## 설계에서 정한 것

- **파일 단위로 자르지 않는다.** 한 클래스가 세 가지 일을 하면 명세 셋, 다섯 파일이 한 화면을 만들면 명세 하나. 경계가 틀리면 이후가 전부 틀리므로 목록을 먼저 보여주고 동의받는다.
- **관측되지 않으면 존재하지 않는다.** 내부 캐시, 리팩터링 흔적, 최적화는 사용자가 체감하는 결과로 환산되지 않으면 지운다.
- **모르는 것은 추측하지 않는다.** "아마 이렇게 하려던 것"은 `열린 질문`으로 간다. 현재 동작이 버그로 보여도 관측된 대로 적고 의심은 따로 적는다. 명세를 쓰면서 조용히 고치지 않는다.
- **Acceptance는 손으로 따라 할 수 있어야 한다.** 코드를 열어야 확인되는 항목은 Acceptance가 아니다. 린터가 이걸 잡는다.

## 한계

- 코드가 없는 신규 기능에도 같은 틀을 쓸 수 있지만, 관측면 수집을 사용자 인터뷰로 대체해야 한다.
- 산출물 예시 파일은 references 안의 한 건뿐이다.
