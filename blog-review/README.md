# blog-review

테크 블로그 글 하나를 **대화형으로** 리뷰해 학습 노트로 남긴다. 요약을 대신 해주는 스킬이 아니다.

## 왜 만들었나

블로그 요약을 받아 읽으면 그 순간은 이해한 것 같지만 내 것이 되지 않는다. 오래 남는 건 확인된 것이 아니라 **교정당한 것**이다. 직접 겪기 힘든 엔지니어링 상황을 대리 경험하고, 비슷한 문제가 닥쳤을 때 빠르게 접근할 수 있는 사고 자산으로 쌓으려면 내가 먼저 말을 해야 한다.

## 무엇을 해주나

1. 글을 가져와 메타데이터 · 중립 요약 · 뼈대만 깔고 **멈춘다.** 여기서 평가나 교훈을 넣지 않는다.
2. 사용자가 "내가 이해한 것 / 생각 / 질문"을 날것으로 던진다. 제일 값진 단계다.
3. ✅ 맞음 / 🔧 교정 / 💡 한 단계 더로 반응한다.
4. 노트로 묶어 저장한다. 범용 개념은 개념 사전으로 분리하고, 교정 전 원문은 JSONL로 보존한다.

산출물은 학습 노트 `.md` + 개념 파일 + raw `.jsonl`이다.

## 어떻게 쓰나

묶음에 없다. 폴더 복사로 설치한다 → [설치](../docs/install.md)

> 이 글 같이 읽자 (URL)
> /blog-review URL

절차는 [SKILL.md](SKILL.md)에 있다.

## 설계에서 정한 것

- **해석을 먼저 깔지 않는다.** 내 해석을 먼저 보여주면 사용자는 그걸 따라 읽고, 그 순간 리뷰는 실패한다.
- **방법만 담고 값은 프로젝트가 정한다.** 저장 경로, 태그 어휘, 진행 주기, 노트 깊이 기준은 사람마다 다르다. 스킬은 "정해야 한다"만 말하고, 값은 프로젝트의 `AGENTS.md`에서 읽는다. 이 repo의 [취향 분리 원칙](../docs/principles.md)이 이 스킬에서 나왔다.
- **그래서 묶음에 없다.** 플러그인으로 깔면 프로젝트 설정 없이 바로 쓸 것처럼 보이는데, 이 스킬은 프로젝트 규칙이 먼저다.
- **교정 전 원문을 남긴다.** `scripts/write_raw.py`가 노트와 raw 파일이 형제 디렉터리인지 검증한다. 이 두 경로만은 프로젝트가 바꿀 수 없다.

## 한계

- 사용자가 말하지 않으면 진행되지 않는다. 시간이 없으면 3단계(날것 던지기)까지만 하고 끝낸다.
- 글을 대신 요약하는 용도로 쓰면 이 스킬이 막는다.
