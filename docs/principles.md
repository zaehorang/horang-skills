# 이 repo의 원칙

## vendor 이름을 본문에 쓰지 않는다

특정 도구 이름 대신 능력으로 쓴다 — "웹 페이지를 가져온다", "파일로 저장한다". 그래야 어느 에이전트에서든 돈다.

단, **특정 도구를 제어하는 것 자체가 목적인 스킬은 예외다.** 도구 이름이 곧 내용이라 추상화하면 스킬이 할 일이 없어진다 (`herdr-dispatch`, `harness-backlog`).

## README.md는 사람용, SKILL.md는 에이전트용

- `SKILL.md`: 에이전트가 읽는 절차. 트리거, 순서, 규칙, 검사.
- `README.md`: 사람이 읽는 설명. 왜 만들었나, 무엇을 해주나, 설계에서 정한 것과 이유, 한계.

**절차는 SKILL.md에만 쓴다.** 둘에 같은 절차를 두면 어긋난다. README는 SKILL.md를 가리키기만 한다.

`examples/` 안의 README는 그 예시 폴더의 안내서라 이 규칙과 별개다.

## 개인 취향을 스킬에 넣지 않는다

판별 기준:

> *"다른 사람이 이 스킬을 깔았을 때, 이 줄이 그 사람에게도 참인가?"*

| 답 | 어디로 |
|---|---|
| 참이다 | **스킬** — 방법 |
| "내가 그렇게 정했다" | **프로젝트** — 결정 |
| 참이지만 **값이 사람마다 다르다** | 스킬엔 *"정해야 한다"* 만, **값은 프로젝트** |

세 번째가 제일 놓치기 쉽다. 예를 들어 `blog-review`의 태그 어휘는 스킬에 두면 안 된다 — **개인 어휘를 늘리려고 공유 스킬을 고치게 되면 분리가 잘못된 것이다.**

## 검사는 스크립트가 먼저, 눈은 나중

산출물을 내는 스킬은 결정적 검사 스크립트를 같이 둔다 (`deck_verify.py`, `report_tool.py check`, `check_explainer.py`, `check_world.mjs`, `lint_spec.py`). 모델이 "괜찮아 보인다"고 하기 전에 스크립트가 넘침·대비·누출을 잡는다. 눈 검토는 스크립트가 통과한 뒤에 한다.
