# explorable-world

부품이 여럿인 시스템을 **비유 세계관 지도**로 바꾸고, 사건을 일으켜 요청의 흐름을 탐험하며 이해하는 웹 페이지 폴더를 만든다.

**예시:** [k8s harbor](https://zaehorang.github.io/horang-skills/explorable-world/examples/k8s-harbor/) — 쿠버네티스 클러스터를 항구로, 사건 "앱 배포하기" 7장면. 데스크톱 화면에서 연다.

## 왜 만들었나

부품이 많은 아키텍처는 "누가 누구에게 무엇을 보내나"가 핵심인데, 네모와 화살표 도식으로는 그 흐름이 머리에 안 들어온다. 처음부터 설명을 다 보여주는 문서는 읽다 지치고, 비유만 있는 동화는 실제와 연결이 안 된다. 살아 움직이는 세계를 먼저 보고, 사건을 일으켜 흐름을 따라가고, 궁금한 만큼만 깊이 들어가는 쪽이 남는다.

## 무엇을 해주나

- 부품을 장소 · 인물 · 물건으로 바꾼 아이소메트릭 지도. 쿠버네티스는 항구, 네트워크는 우편 도시.
- 사건 버튼을 누르면 요청이 지도를 오가는 애니메이션이 재생된다.
- 설명은 3겹이다. 자막(늘 보임) → 더 보기 패널 → 실제로는?(그 순간의 실제 명령 · 저장 기록 · 출력).
- 이름은 색으로 구분한다. 파랑 공식 용어 · 노랑 직접 지은 이름 · 회색 자동 생성. 마우스를 올리면 이유가 뜬다.

맞는 주제는 쿠버네티스 컨트롤 플레인, 마이크로서비스 주문 처리, CI/CD, 메시지 큐, OAuth 네 주체처럼 부품이 많고(6개 이상) 각 부품의 내부는 얕은 것이다.

## 설계에서 정한 것

- **부품 전부를 한 지도에.** 부품 하나를 열어 안의 상태 변형을 깊이 보는 건 [`mechanism-explainer`](../mechanism-explainer)다. 두 스킬은 같은 주제를 다른 깊이로 나눈다.
- **비유와 실제가 다른 곳은 말로 밝힌다.** "크레인이 상자를 옮기지만 실제로는 장부에 한 줄을 적을 뿐"처럼, 비유가 실제를 오해하게 만드는 지점을 반드시 한 번 짚는다.
- **"실제로는?"은 진짜 형식만.** 실제 명령, 실제 API 경로, 실제 로그 형식. 값은 단순화해도 형식은 지어내지 않는다. 확인 못 한 이름은 `Example CA`처럼 가짜임이 분명하게 쓴다.
- **엔진은 공용, 주제는 파일 3개.** `index.html · style.css · iso.js · engine.js`는 주제마다 고치지 않고 `world.js · content.js · world.css`만 쓴다. 엔진에 기능이 필요하면 스킬의 `engine/`을 고쳐 모든 세계가 같이 좋아진다.
- **코드로 먼저, 눈으로 나중.** `scripts/check_world.mjs`가 이름 규칙과 블록 사이 일관성을 잡는다.

## 한계

- 데스크톱 브라우저 전용이다. 모바일 · 터치는 만들지도 검사하지도 않는다.
- 알고리즘, 변환 파이프라인, 런타임 내부처럼 부품 하나의 상태를 따라가는 주제에는 맞지 않는다.
