# ios-video-qa

앱 레포의 `qa/`(qa.config, states.sh, flows.sh, cases/, steps/, gaps.json)를 읽고 엔진 명령 `qa`로 실행한다. 엔진은 앱을 모른다.
엔진 폴더는 이 SKILL.md가 있는 폴더다(이하 `$ENGINE`). 명령은 `$ENGINE/scripts/qa <명령>`이고, 앱 레포(또는 그 아래)에서 부른다.

## 파일 안내

| 파일 | 언제 읽나 |
|---|---|
| `references/commands.md` | 명령·종료 코드·qa.config 키가 필요할 때 |
| `references/case-format.md` | 각본(md)을 쓰거나 고칠 제안을 할 때 |
| `references/script-vocabulary.md` | 스크립트(steps/*.sh)·flows·states를 쓸 때. 판정 함수, 읽기, 질의, 금지 어휘 |
| `references/approvals.md` | 승인·질문·선택 규칙 상태를 설명하거나 사람에게 요청할 때 |
| `references/verify.md` | 재현 검증 결과(검증 불가·판정 결함)를 읽을 때 |
| `references/keyboard-packs.md` | 화면 키보드 입력이 실패하거나 다른 언어 자판이 필요할 때. 기기·화면 비율 가정 |
| `examples/memo-app/qa/` | 각본·스크립트 형식의 완성 예(가상의 메모 앱) |
| `scripts/pages/adapters/<이름>/README.md` | 공유 페이지를 발행할 때(사용자가 발행을 확인한 뒤) |

## 절대 규칙

- **승인·답·판단은 사람만 한다.** `qa approve`, `qa answer`, `qa judgments`는 에이전트 환경에서 거부된다. 우회하지 않는다(환경 변수 비우기, 터미널 흉내, 기록 파일 직접 쓰기·고치기 모두 금지). 필요하면 사람에게 `! $ENGINE/scripts/qa approve <ID>`처럼 요청하고 멈춘다.
- **사람 승인 전 결과를 통과로 보고하지 않는다.** `qa run`이 exit 5(사람 승인 대기)면 그대로 전한다. `QA_ALLOW_UNAPPROVED=1`은 엔진 자체를 시험할 때만 쓰고, 그 결과는 "사람 승인 전"으로만 보고한다.
- **합격 기준을 약하게 만들지 않는다.** 각본(md)을 고쳐야 할 것 같으면 고치지 말고 "각본 수정 제안"으로 보고한다. 판정을 지우거나 `skip`·`--any`·느슨한 질의로 바꿔 통과시키지 않는다.
- **판정은 판정 함수로만**, 피연산자는 출처 있는 읽기(`ui_read`)로만 한다. 셸 식, 상수끼리 비교, 근거 파일·엔진 변수를 건드리는 어휘는 실행 전 검사가 막는다(`references/script-vocabulary.md`).
- **모호하면 멈추고 묻는다.** 후보가 여럿이면 `--first/--last/--nth`와 `# 규칙: G번호`를 함께 쓰고, 규칙이 없거나 승인 범위 밖이면 질문을 만들고 멈춘다. 대신 정하지 않는다.
- **외부 게시는 사용자 확인 뒤에.** 공유 페이지 발행, PR 댓글은 미리보기를 보여 주고 확인을 받은 뒤에만.
- 전역 설정(시뮬레이터 하드웨어 키보드 연결)은 실행이 잠금을 잡고 바꾸고 되돌린다. 손으로 바꾸지 않는다. 기기를 추가·삭제하지 않는다.

## 절차

### 처음 설치(앱 레포에 qa/가 없을 때)
1. `qa init` → `qa/`가 생긴다. 프로젝트·스킴·기기는 찾을 수 있으면 채워진다.
2. `qa doctor` → FAIL을 사용자와 함께 고친다(qa.config 값, 기기 이름).
   - 사람마다 다른 값은 사용자가 정해야 한다: 조건 이름과 기기, 결과 보존 기간, 검증 불가 상한, 앱의 하루 경계 시각. 값은 `qa.config`에 적게 하고 대신 정하지 않는다. 비워 두면 엔진 기본값(`references/commands.md`)이 쓰인다고 알린다.
3. 첫 각본(QA-01)의 '첫 화면의 문구'를 앱의 실제 문구로 바꾸는 것은 각본 변경이므로 사용자에게 확인받는다.
4. `qa check` → exit 5(사람 승인 대기)면 사람에게 `qa approve QA-01`을 요청하고 멈춘다.

### 실행(`/qa run`)
1. `qa check [ID…]`. exit 2면 차단 이유를 그대로 전하고, 스크립트 문제면 고친다(각본은 고치지 않는다). exit 5면 대기 목록을 전하고 멈춘다.
2. `qa run [ID…] [--condition 이름]`. 끝나면 `results/latest/index.html`과 REPORT.md를 읽고 요약한다.
3. 실패는 보고서의 진단(준비 실패·질문 대기·환경·스크립트·판정 불가·앱 버그 또는 각본 낡음)을 따라 분류하고, "확인된 사실"과 "AI 분석"을 나눠 쓴다.
4. 재현 검증이 막았으면(판정 결함, 검증 불가 상한 초과, 근거 위조 의심) 그 판정을 고친다. 결함을 무시하고 통과로 보고하지 않는다.
5. 스크립트를 고치면 다음 실행이 `steps/.changes/`에 diff를 남기고, 승인본과 다르면 사람 재승인이 필요하다고 전한다.

### 새 각본(`/qa new`, S0~S7)
1. S0 `qa new <ID> "<제목>" <영문-요약>` → 각본 초안을 쓴다(사용자가 하는 일·보이는 것만, 화면 문구로). `qa stage <ID> S0`.
2. S1 탐색 스크립트를 쓰고 `qa sim <ID> <탐색 스크립트>`: `explore_dump`로 화면을 보고 항목마다 `locate_record n.k <질의>`. **고르지 않는다.** → `qa stage <ID> S1`.
3. S2 `qa stage <ID> S2`: 코드가 후보 여럿·후보 없음·모호한 기대값을 질문으로 만든다. 해석이 필요한 질문은 `approve.py gap-add --origin ai`로 더한다. **답 없는 blocking 질문이 있으면 멈추고** 질문 목록과 `qa review` 페이지를 건넨다.
4. S3 답(선택 규칙)대로 `steps/<ID>.sh`를 쓴다(`@항목ID`, `# 규칙: G번호`). `qa stage <ID> S3`.
5. S4 `qa stage <ID> S4`: waiting이면 사람에게 `qa approve <ID>`(각본+스크립트)와 필요한 `qa answer G번호 --bind`를 요청하고 멈춘다.
6. S5~S7 `qa stage <ID> S5`, `S6`, `S7`. 앞 단계를 다시 하면 뒤 단계는 stale이 된다.

### 리뷰·공유
- `qa review [결과]` → 로컬 페이지. 사람이 판단·답·승인 요청을 JSON으로 내려받아 직접 `qa judgments|answer|approve --from <파일>`로 반영한다.
- `qa share [결과] --adapter <이름>` → 공유 묶음을 만들기만 한다. 발행은 어댑터 README 절차대로, 사용자 확인 뒤.
