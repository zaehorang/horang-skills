# mechanism-explainer

시스템 · 도구 · 알고리즘 **하나**의 내부 동작을 단계별로 따라가며 이해하는 단일 HTML 파일을 만든다.

**예시:** [컨테이너 오케스트레이션](https://zaehorang.github.io/horang-skills/mechanism-explainer/references/examples/container-orchestration.html) — 앱이 격리된 실행 단위가 되고 스스로 복구되기까지 9단계

## 왜 만들었나

내부 동작을 글로 읽으면 "상태가 단계마다 어떻게 바뀌는지"가 잡히지 않는다. 개념 요약 문서는 결과만 말하고, 도식 한 장은 한 시점만 보여준다. 정작 알고 싶은 건 **이 단계가 끝나면 데이터 · 메모리 · 상태가 어떻게 달라져 있나**이고, 그건 눈으로 전후를 비교해야 들어온다.

## 무엇을 해주나

- 축(spine) 하나를 정하고, 단계마다 **같은 다이어그램의 상태가 바뀌는** 페이지를 만든다.
- 단계마다 실제 코드 · 로그 · 페이로드의 before/after가 나란히 보인다.
- 독자가 조작으로 직접 깨뜨려 보며 "이 단계가 없으면 무엇이 무너지나"를 확인한다.
- 의존성 없는 단일 `.html`로 프로젝트 안에 남는다. 채팅 미리보기가 아니다.

맞는 주제는 번들링 · 컴파일 · 렌더링 같은 변환 파이프라인, 정렬 · GC 같은 알고리즘, 이벤트 루프 같은 런타임, 핸드셰이크 · 합의처럼 상태 전이가 핵심인 것이다. 부품은 적고(1~4개) 상태는 깊다.

## 설계에서 정한 것

- **부품 하나를 연다.** 부품 여럿을 한 지도에 펴놓고 누가 누구에게 보내는지 보는 건 [`explorable-world`](../explorable-world)다. 같은 쿠버네티스라도 스케줄러 하나의 필터 · 점수는 이 스킬, 컨트롤 플레인 전체의 배포 흐름은 저쪽이다.
- **이름이 아니라 역할로 부른다.** 용어는 그 용어가 처음 나온 단계 안에서 푼다. 내가 지어낸 비유 어휘는 1단계에 범례로 고정한다.
- **글이 무대를 밀어내지 않는다.** 단계당 280자. 글이 길어지면 설명 문서가 되고, 보여주는 페이지가 아니게 된다.
- **코드로 먼저, 눈으로 나중.** `scripts/check_explainer.py`가 구조와 글자 수를 잡고, 브라우저 검사가 그 뒤다.

## 한계

- 상태 변형이 없는 개념 비교(REST vs GraphQL)나 설치법 같은 사용법에는 맞지 않는다. 글과 표가 낫다.
- 그래프 한 장으로 끝나는 것(Big-O 비교)에도 과하다.
