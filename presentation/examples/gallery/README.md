# 발표 장 갤러리 — 사내 문서에 답하는 에이전트

발표에 자주 나오는 장 22가지를 한 주제로 하나씩 채운 견본이다. 실제 덱을 만들 때 **장 종류와 색 테마를 고르고, 해당 `<section>`을 복사해 내용만 바꾸는** 기준이 된다.
FLOW·SCRIPT를 거친 완성 발표 예시는 [`../snack-drawer/`](../snack-drawer/)에 있다. 이 폴더는 **장 견본**이라 대본 없이 화면만 둔다.

## 여는 법

| 파일 | 무엇을 보나 |
|---|---|
| **`index.html`** | 장 갤러리. 카드로 미리 보고, 누르면 크게 열린다(← → 이전/다음, Esc·× 닫기). 위쪽 버튼으로 테마와 바탕(미색·흰색)을 바꿔 본다 |
| **`themes.html`** | 색 테마. 위쪽에서 테마 하나와 바탕(미색 · 흰색 · 나란히)을 고르면, 아래에 그 테마의 용도·덱에 쓸 코드·팔레트와 대표 장 6개만 나온다. "나란히"는 같은 장을 미색·흰색 좌우로 견준다. 카드를 누르면 크게 보기(← → · Esc · ×) |
| `palette.html?theme=이름` | 테마 하나의 팔레트 장. 역할별 색과 실제 대비 수치를 토큰에서 읽어 보여준다 |
| `presentation.html#7` | 견본 덱 자체. `#번호`로 그 장부터 연다 |

주소 옵션 — `?theme=duo` 테마 · `?paper=white` 흰 바탕 · `?embed` 조작 버튼과 키 입력 없이(미리보기용). 덱 파일은 고치지 않는다.

## 파일이 나뉘는 방식

```
gallery/
  index.html         장 갤러리 페이지 (카드 + 크게 보기). 장 목록·설명은 이 파일의 GROUPS 배열
  themes.html        테마 페이지 (위쪽 선택 → 아래 그 테마만). 테마 목록·용도는 THEMES, 보여 줄 장은 SAMPLES 배열
  palette.html       팔레트 장 한 장짜리 덱 (스타터 CSS + 팔레트 전용 CSS + 스와치)
  presentation.html  견본 덱 22장 (스타터 CSS·엔진 + 견본 장)
  presentation.pdf   견본 덱 PDF
  assets/            SCENE.svg(3장 장면) · SCREEN.svg(8장 제품 화면 목업)
```

`presentation.html`과 `palette.html`의 `<head>`(CSS)와 엔진은 **스타터(`assets/starter/presentation.html`)와 같아야 한다.** `deck_selftest.py`의 `gallery-sync`가 이를 검사한다. 스타터 CSS를 고치면 두 파일에도 옮긴다.

덱 한 파일 안은 세 덩어리다.

1. **CSS** — 색 3층(팔레트 원색 → 의미 토큰 → `[data-theme]` 테마, 그 위에 `[data-paper]` 바탕) · 타이포 스케일 · 레이아웃(본문은 제목 바로 아래 같은 위치에서 시작) · 패턴별 CSS
2. **장** — `<section class="slide" data-title="…">` 하나가 한 장. `slide-head`(kicker + 결론형 제목) / `content`(패턴) / `foot`(보조 문구 + 쪽 번호)
3. **엔진** — 화면 맞춤 축소, 장 넘김(키·버튼·`#번호`), 쪽 번호 자동 채움, 구조도 선 그리기

각 장 푸터의 점선 **견본** 표시(`<span class="guide">`)는 안내문이다. 복사한 덱에 남아 있으면 `deck_verify`가 경고한다.

## 장별 구성

| 장 | 패턴 | 만드는 화면 | 나뉨 (구조) |
|---:|---|---|---|
| 1 | A 표지 | 주제와 한 줄 약속을 어두운 바탕에 | `.cover-content.text-only` 1열 — kicker · 제목 2줄(강조어 `.accent`) · 부제 · 한 문장 상자 |
| 2 | U 목차 | 네 덩어리의 순서와 시간, 지금 위치 | `ol.agenda` 4행 — 행마다 번호 · 제목+부제 · 시간. 지금 항목 `.now`, 지난 항목 `.done` |
| 3 | C 문제 장면 | 흩어진 문서를 찾는 상황 | `.split` 2열 — 왼쪽 장면 그림 + 큰 문구 오버레이 / 오른쪽 상황 한 줄 · 현장 한 마디 · 결과 4개 · 결론 |
| 4 | Q 개념 설명 | RAG의 검색·증강·생성 세 단계 | `.dg-legend-split` 2열 — 왼쪽 구조도(노드 6, 번호 3) / 오른쪽 번호 범례. 번호 = 말하는 순서 |
| 5 | O 구조 설명 | 미리 쌓는 흐름과 질문 때 흐름이 만나는 곳 | `.dg` 안에 레인 2개(위 질문할 때 · 아래 미리 해 둘 일). 만나는 두 노드를 같은 열에 둬 왕복선이 곧다. 짚는 곳은 `.new` 노드 하나 |
| 6 | J 두 시점 흐름 | 새 문서와 고친 문서가 반영되는 두 시점 | `.ai-flow-grid` 2열 카드 — 카드마다 시점 라벨 · 제목 · 칩 4개(→로 연결) · 결과 한 줄 |
| 7 | S 코드 설명 | 검색 노드 코드가 state의 무엇을 바꾸는지 | `.walk` 2열 — 왼쪽 단계 레일(지금 단계만 펼침) / 오른쪽 코드 블록(강조 줄 2곳에 번호) + 결과 칸 2개(같은 번호) |
| 8 | M 화면 시연 | 답과 근거 카드를 받는 제품 화면 | `.shot-split` 2열 — 왼쪽 화면 캡처 + 핀 3개 / 오른쪽 핀 번호별 설명 |
| 9 | L 사용자 여정 | 질문부터 문서 수정까지 5단계 | `.screens` 5열 — 단계마다 와이어프레임(바뀌는 곳 하나만 칠함) + 번호 · 이름 · 한 줄 |
| 10 | K 행동과 API | 사용자 행동 4개와 API 4개의 짝 | `.api-layout` 2열 — 왼쪽 행동 카드 / 오른쪽 API 행. 같은 번호·같은 행 높이, 짚는 행 하나 `.hot` |
| 11 | B 두 쪽 대비 | 줄어드는 일과 남는 일 | `.thesis-grid` 2열 카드 — 추세 라벨 · 제목 · 근거 3개 · 결론. 강조는 남는 쪽 하나 |
| 12 | P 전후 비교 | 검색기를 더하면 흐름이 어떻게 바뀌나 | `.dg-compare` 2패널 — 같은 열·같은 행 높이의 뼈대 둘. 왼쪽은 흐리게(`.soft`), 새것(`.new`)은 오른쪽에만 |
| 13 | R 항목별 짝 비교 | 약점 6개와 해결 6개 | `.rowmap` 3열 — 왼쪽 글자(갈래 A) · 가운데 점선 화살표 · 오른쪽 상자(갈래 B), 6행 |
| 14 | D 문제→기능 매핑 | 문제 5개에 기능 5개 대응 | `.matrix` — 윗줄 문제 5칸 / ↓ / 아랫줄 기능 5칸(짚는 칸 `.hot` 하나) / 결론 띠 |
| 15 | V 핵심 숫자 | 정답률 54% → 81% | `.stat-hero` 2열(가운데 정렬 예외) — 왼쪽 큰 숫자 + 무엇의 숫자인지 / 오른쪽 맥락 · 비교 기준 2행 · 출처 |
| 16 | T 데이터 표 | 검색 방식 4가지를 같은 기준으로 | `table.data-table` 4행×5열 — 숫자 열 `.num` 오른쪽 정렬, 짚는 행 `.hot` 하나, 아래 결론 · 출처 |
| 17 | N 분석 그림 | 질문 유형별 정답률 막대 | `.figure-content` — 전폭 그림 · 결론 한 줄 · 출처. 그림은 인라인 SVG라 막대 색이 테마 토큰을 따른다 |
| 18 | H 구성과 상태 | 부품 5개와 각각의 구현 상태 | `.architecture` — 위 단계 칩 5개(카드 열에 맞춤) / 아래 부품 카드 5개(확인됨·제안·예정) / 푸터 범례 |
| 19 | E 우선순위 대상 | 가장 먼저 바뀌는 사람 | `.impact-layout` — 큰 1순위 카드 1 + 작은 카드 4. 강조는 1순위 카드에만 |
| 20 | F 역할 분담 | 에이전트와 사람의 책임 경계 | `.before-after` 2열 + 가운데 ＋ — 역할 라벨 · 제목 · 항목 3개. 강조는 결론 쪽 카드(`.key`) 하나 |
| 21 | G 로드맵 | 완료 · 승인 대기 · 분기 말 3단계 | `.roadmap` 3열 — 위 연결선과 단계 원 / 아래 카드. 원은 카드 상태(`.done` · `.now`)를 따른다 |
| 22 | I 지표와 결정 요청 | 승인받을 것과 판단 기준 | 위 `.decision`(결정 3개, 가장 큼) / 아래 `.metric-list` 4열 지표(목표와 측정 방법) |

같은 이야기를 여러 패턴으로 반복하는 장이 있다(예: 5·6장, 11·20장). 패턴을 보여주려는 견본이라서이고, 실제 덱에서는 하나만 고른다.

## 색 테마

| 테마 | 어울리는 발표 |
|---|---|
| `clay` (기본) | 제안서·결과 보고. report 보고서와 같은 톤 |
| `ocean` | 기술 설명·아키텍처·데이터 리뷰 |
| `duo` | 강의·교육·비교. 남색 갈래 A + 자홍 강조 |
| `forest` | 운영 현황·성과 보고 |
| `signal` | 피치·키노트·외부 발표. 흰 바탕 고대비 + 빨강 한 점 |

바탕은 기본 미색이고, 어느 테마에나 `data-paper="white"`를 겹쳐 흰 바탕으로 바꿀 수 있다(바꾸는 건 `--paper` 하나).

테마가 달라도 역할은 같다 — 강조는 지금 짚는 곳 하나, 갈래 A·B는 이쪽·저쪽(강조색이 아님), 구현 상태는 확인됨·제안·예정, 번호 원은 먹색. 덱의 `<html lang="ko">`에 `data-theme="ocean"`을 붙이면 바뀐다. 새 테마 만드는 법과 대비 기준은 [`references/build.md`](../../references/build.md)의 "색 바꾸기".

## 자산과 수치

`assets/`의 그림 둘(`SCENE.svg`·`SCREEN.svg`)은 견본용으로 직접 그린 파일이라 테마를 따르지 않는다. `SCREEN.svg`는 제품 화면 **목업**이고 실제 덱에서는 제품 캡처로 바꾼다. 17장 차트는 인라인 SVG에 토큰 색을 줘서 테마를 따른다. 15·16·17장의 수치는 레이아웃 견본용 예시 데이터이며 장 안에도 그렇게 적었다.
