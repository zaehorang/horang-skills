# deck-narrate

**슬라이드보다 대본이 먼저다.** 화면을 먼저 만들면 "무엇을 말하고 싶은지"가
레이아웃에 끌려간다. 말이 서면 화면은 그 말의 근거만 담으면 된다.

FLOW 와 SCRIPT 는 축이 다르다.

- **FLOW = 장의 배열(가로)** — 몇 장이고, 각 장이 답하는 질문과 주장이 무엇인가
- **SCRIPT = 장 안의 전개(세로)** — 그 주장에 도달하기까지 말이 어떤 순서로 이어지는가

FLOW 가 *무엇을 주장하는가* 라면 SCRIPT 는 *어떻게 믿게 만드는가* 다.

두 패스로 쓴다. 각 패스마다 사용자 승인을 받고 넘어간다.

---

## 1패스 · 요지

장별로 **말의 박자 3~6개**만 적는다. 완성 문장으로 쓰지 않는다.
여기서 구조 결함이 싸게 드러난다. 완성 발화체로 쓴 뒤 구조가 틀리면 통째로 다시 쓴다.

```markdown
## 4장 · 질문하면 무엇을 받는가 — 65초

1. 앞 장의 그 질문을 실제로 던진다            (전환)
2. 답변과 신뢰 상태가 함께 온다 — SUPPORTED
3. 그런데 확인할 게 있다 — 참고한 문서가 이후 수정됨
4. 인용 카드로 당시 버전을 직접 열어볼 수 있다
5. 그래서 답만 받는 게 아니라 근거까지 받는다  (결론)
```

FLOW 한 행에 도달하는 다섯 박자다. FLOW 를 다시 쓰는 것이 아니다.

### 1패스 자가 점검

- **논리 없음** — 요지가 FLOW 표를 문장으로 옮긴 수준인가.
  그렇다면 그 장은 주장만 있고 설득 경로가 없다. 박자를 다시 찾는다
- **박자 비약** — 앞 박자 없이 새 개념이 튀어나오는 지점이 있는가
- **밀도** — 한 장의 박자가 7개를 넘거나 예상 대본이 다른 장의 두 배가 되면
  **장을 나눌 신호다.** 대본 길이는 정보 밀도의 가장 정직한 지표다
- **박자 부족** — 박자가 2개 이하면 그 장은 다른 장에 흡수될 수 있다

구조 문제가 나오면 **FLOW 로 돌아가 고친다.** 되돌아가는 것이 이 단계의 존재 이유다.
FLOW 를 고쳤으면 무엇을 왜 바꿨는지 사용자에게 말한다.

**승인을 받고 2패스로 간다.**

---

## 2패스 · 완성 발화체

실제 말할 문장으로 쓰고, 장마다 화면과 말을 가른다.

```markdown
## 4장 · 질문하면 무엇을 받는가 — 65초

(발화체 본문)

> **화면에 둘 것**: 질문 1건, 답변 + SUPPORTED 배지, 인용 카드 2장, 우측 질문 API
> **말로만 할 것**: 왜 버전을 보존하는지, 참고 문서가 답변 이후 수정됐다는 사실
```

**이 두 줄이 `deck-build` 의 입력 명세다.**
"화면에 둘 것" 이 그 장의 정보 예산이고, "말로만 할 것" 은 슬라이드에 넣으면 안 되는 목록이다.
이 구분이 없으면 대본을 그대로 옮긴 텍스트 덤프 슬라이드가 나온다.

슬라이드는 대본이 아니라 **청중이 3초 안에 결론을 잡게 돕는 근거**다.

---

## 문체

### 다음 장을 예고하지 않는다

각 장은 그 장에서 끝난다. "다음은 ~를 보겠습니다" 를 붙이지 않는다.
예고는 청중의 주의를 화면 밖으로 보내고, 장 순서를 바꿀 때마다 대본을 고치게 만든다.
전환이 필요하면 **다음 장의 첫 문장**이 받는다.

### 수사적 질문은 기본으로 쓰지 않는다

"~한 적 있으신가요?" 같이 청중에게 던지는 질문은 **사용자가 요청할 때만** 쓴다.
기본은 평서문으로 상황을 놓는다.

```
✗ 혹시 팀 프로젝트를 하면서 근거를 다시 찾지 못했던 경험 있으신가요?
✓ 팀 프로젝트를 하다 보면, 무엇을 결정했는지는 기억나는데
  왜 그렇게 결정했는지는 찾기 어려울 때가 있습니다.
```

### 도입

인사 → 상황 → 그 상황을 대표하는 구체적인 예 → 오늘 무엇을 말할지. 네 박자면 충분하다.

### 화면 설명은 가볍게

화면이 **무엇을 나타내는지 한 줄**, 그리고 **뭐가 있는지 가볍게.**
화면에 보이는 항목을 하나씩 낭독하지 않는다. 청중은 이미 보고 있다.

```
✗ 화면에는 클라이언트별 토큰 갱신과 만료 시점이 달라 재인증 동작이 일관되지
  않았고, 이를 서버에서 통합 관리하기로 했다는 답변이 표시됩니다.
✓ 질문을 보내면 답변과 함께 판단에 필요한 근거가 반환됩니다.
  먼저 답변과 신뢰 상태가 표시됩니다. 지금은 충분한 근거를 찾았기 때문에 SUPPORTED입니다.
```

### 문장

짧게 끊는다. 한 문장에 주장 하나. 번역투와 명사 나열을 피한다.
읽었을 때 숨이 차는 문장은 두 개로 나눈다.

### 정직성

덱의 구현 상태 표기를 대본도 지킨다.

- `현재 확인됨` → "이렇게 동작합니다"
- `제안` → "이렇게 바꾸려고 합니다"
- `예정` → "다음 단계에서 붙입니다"

와이어프레임을 실제 캡처인 것처럼 말하지 않는다.

## 참고 · 완성 대본 예시

실제 발표에서 쓰인 대본이다. 예고 없음, 수사적 질문 없음, 짧은 문장, 화면 낭독 없음.

```markdown
## 1장 · 흩어진 팀 기록을, 확인 가능한 근거로 — 30초

안녕하세요. 팀 검색 에이전트 SYNAPSE를 발표할 OOO입니다.

팀 프로젝트를 하다 보면,
무엇을 결정했는지는 기억나는데 왜 그렇게 결정했는지는 찾기 어려울 때가 있습니다.

예를 들어 이런 질문입니다.
"웹과 모바일의 인증 방식을 왜 서버 세션으로 통합하기로 했지?"

분명 이전에 논의했던 내용인데, 막상 그 이유를 다시 확인하려면 생각보다 쉽지 않습니다.

오늘은 해당 문제를 SYNAPSE로 어떻게 해결하고자 하는지 말씀드리겠습니다.

## 2장 · 어디에서 봤는지 기억나지 않는다 — 25초

첫 번째 문제는 기록이 여러 곳에 흩어져 있다는 점입니다.

"Slack 어느 채널이었지?" "Notion 어느 페이지였지?" "GitHub 몇 번 PR이었지?"

필요한 정보는 이미 남아 있지만,
위치를 기억하지 못하면 여러 플랫폼을 반복해서 찾아야 합니다.

즉, 기록이 어디에 있는지를 알아야만 찾을 수 있습니다.

## 4장 · 질문하면 무엇을 받는가 — 65초

그럼 처음 봤던 질문을 SYNAPSE에 실제로 던져보겠습니다.

질문을 보내면 답변과 함께 판단에 필요한 근거가 반환됩니다.

먼저 답변과 신뢰 상태가 표시됩니다. 지금은 충분한 근거를 찾았기 때문에 SUPPORTED입니다.

그 아래에는 추가로 확인할 내용이 나옵니다.
현재는 참고했던 Notion 문서가 답변 이후 수정됐다는 사실을 알려주고 있습니다.

맨 아래 인용 카드에서는 어느 문서의 어느 버전을 참고했는지 확인할 수 있습니다.

오른쪽 API에서도 질문 하나에 대해 답변, 상태, 확인 사항, 인용 정보가 함께 반환됩니다.

즉, 답만 받는 것이 아니라 그 답의 근거까지 확인할 수 있습니다.

> **화면에 둘 것**: 질문 1건, 답변 + SUPPORTED 배지, 확인 사항 1줄, 인용 카드 2장, 우측 질문 API
> **말로만 할 것**: 왜 버전을 보존하는지, 인용 카드를 눌러 원문으로 갈 수 있다는 점
```

2장에서 3장으로 넘어갈 때 예고가 없다는 점을 본다. 2장은 2장에서 끝나고,
3장의 첫 문장("그런데 원문을 찾았다고 끝나는 것도 아닙니다")이 전환을 받는다.

## 산출물

`SCRIPT.md`. 1패스와 2패스가 같은 파일을 덮어 쓴다. 파일 끝에 전체 소요 시간을 둔다.
장이 많으면 범위별로 나눠도 된다 (`SCRIPT_1-5.md`).

## 경계

- 대본만 만든다. HTML 은 만들지 않는다.
- 1패스 승인 없이 2패스로 가지 않는다. 2패스 승인 없이 `deck-build` 로 가지 않는다.
- 사용자가 문구를 직접 고쳐 오면 그대로 존중한다. 되돌리지 않는다.
- 사용자가 "피드백만" 이라고 하면 파일을 고치지 않고 말로 답한다.
